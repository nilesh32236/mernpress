# Multilingual content — developer guide

## Data model

Translations are ordinary posts in the same table:

| Column | Meaning |
| --- | --- |
| `posts.language` | Language code (`en`, `hi`, `pt-br`), default `en` |
| `posts.translation_group` | UUID shared by every variant of one document; defaults to `gen_random_uuid()` |

Unique `(translation_group, language)`; `(language, status)` is indexed.
Existing posts keep `en` and each becomes its own group (migration
`20261106100644_add_post_languages`).

## Configuration

`site_languages` (option store, group `general`, default
`{ default: 'en', enabled: ['en'] }`). The shared normalizer lives in
`packages/contracts/src/languages.ts`:

- codes match `^[a-z]{2,3}(-[a-z]{2})?$`;
- the default is always included in `enabled`;
- invalid/duplicate entries are dropped.

Settings → Languages (`/settings/languages`, administrators write) edits the
list: predefined languages plus custom codes. Changing the default re-prefixes
posts in the old default language; nothing is rewritten.

## Paths

`languagePath(config, language, path)` and `stripLanguagePrefix(config, path)`
are the only prefix rules:

| Language | Document | Public path |
| --- | --- | --- |
| default (`en`) | post `/posts/hello` | `/posts/hello` |
| `hi` | post `/posts/hello` | `/hi/posts/hello` |
| default | page `/about` | `/about` |
| `hi` | page `/about` | `/hi/about` |

Public archives (home, category, tag, author, search) are default-language
only. The sitemap lists every enabled language; a translated variant is never
duplicated into the default feed.

## API

| Route | Behaviour |
| --- | --- |
| `GET /api/admin/languages` | Normalized `{ default, enabled }` (signed-in staff) |
| `PUT /api/admin/languages` | `manage_options`; strict `{ default, enabled[] }` |
| `GET /api/admin/posts/:id/translations` | Sibling rows `{ id, language, title, slug, type, status, updatedAt }` |
| `POST /api/admin/posts/:id/translations` | `{ language }` → 201 draft sibling (`content.create` + edit rights, one per language) |
| `POST/PATCH /api/admin/posts` | accepts `language` (must be enabled) |
| `GET /api/public/posts/:slug?lang=` | single variant in that language |
| `GET /api/public/posts?lang=` | explicit language list (default used when omitted) |
| `GET /api/public/resolve?path=&lang=` | canonical inner path for the middleware |

Creating a translation copies title, excerpt, body and format; it clears
SEO/OG/canonical overrides, terms and comments and derives a
`<source-slug>-<language>` slug. Errors: `400 LANGUAGE_NOT_ENABLED`,
`400 VALIDATION_ERROR` (same language), `409 TRANSLATION_EXISTS`.

## Editor and admin

- The editor language select writes `language` with the post; new posts start
  in the configured default.
- The **Translations** panel is a collapsed `<details>` in the editor sidebar.
  Opening it loads the group; each sibling shows language, status and an edit
  link. The footer creates a draft in any enabled language not yet used, then
  navigates to it.
- The editor gets the language list from `LanguagesProvider` in the admin shell
  (`languages-context.tsx`), so it does not fetch settings on its own.

## Public site

- `apps/web/middleware.ts` strips an enabled non-default prefix, resolves the
  inner path in that language and rewrites to `/posts/<slug>?lang=<code>`
  (or `/<slug>?lang=<code>` for pages).
- `apps/web/app/posts/[slug]/page.tsx` and `app/[slug]/page.tsx` pass `lang` to
  the API.
- `generateMetadata` builds `alternates.languages` with
  `hreflangAlternates`, including `x-default` = default-language URL.
- `LanguageLinks` renders the switcher above the article when published
  translations exist.
- `app/sitemap.ts` loops the enabled languages and lists every variant at its
  own path.

## Per-language menus and theme strings

Two `appearance` options carry the language-aware chrome:

| Option | Shape | Used for |
| --- | --- | --- |
| `customizer_menus` | `Record<language, CustomMenuItem[]>` | Header menu for non-default languages; the default language keeps `customizer_menu` (Appearance → Customize) |
| `theme_strings` | `Record<language, Partial<ThemeStrings>>` | Skip link, footer links, navigation aria labels |

`theme_strings` keys are `skipToContent`, `search`, `blog`, `home`, `feed`,
`primaryNav`, `footerNav`; defaults live in
`packages/contracts/src/theme-strings.ts`. `themeStringsFor(map, language,
defaultLanguage)` merges built-ins → default-language overrides →
request-language overrides.

Request flow:

1. The middleware strips the language prefix and sets `x-mn-language` on the
   forwarded request; the internal `/posts/<slug>` second hop preserves it.
2. The root layout reads the header, sets `<html lang>`, resolves the strings and
   picks `languageMenus[language]` (or `customizer_menu` for the default).
3. Non-default languages never fall back to the default menu or page titles, so
   an untranslated language shows no header navigation rather than English
   labels.

Admin: Settings → Languages (`/settings/languages`) has **Theme strings** (any
enabled language) and **Language menu** (non-default languages, label/URL rows).
API: `GET/PUT /api/admin/theme-strings`,
`GET/PUT /api/admin/language-menus`; writes require `manage_options`.
Public payload: `GET /api/public/site` includes `themeStrings` and
`languageMenus`.

Menu URLs are literal: a Hindi menu uses `/hi/...` paths; nothing is prefixed
automatically. An empty menu removes the override.

### Component strings

`requestThemeStrings(settings?)` in `apps/web/lib/theme-strings.ts` reads
`x-mn-language`, merges the stored overrides and returns a `ThemeStrings` map.
Pages pass it to the components they render:

| Component | Strings used |
| --- | --- |
| `PostView` | written by, min read, category connector, uncategorized, post navigation, comments, related/more headings |
| `AuthorBox` | author heading, website link |
| `RelatedPosts`, `MorePosts`, `PostList` | headings, min-read suffix |
| `Comments` | title/thoughts, reply, leave/cancel reply, notes, name/email/website/comment labels, posting, submit and notices |
| `Pagination` | pagination/previous/next aria labels |
| `SearchForm` | search label, placeholder, button |
| `LanguageLinks` | language-switcher label |
| Archive/search pages | Blog, Category/Tag/Author prefixes, empty-state and search hint/error text |
| `app/not-found.tsx` | 404 title, description and image alt text |

Every component also defaults to `DEFAULT_THEME_STRINGS`, so direct rendering
(tests, isolated use) stays valid. Adding a key is a contract change: append it
to `THEME_STRING_KEYS` (fallback + max length) and use it in the component; the
admin editor lists keys from the API automatically.

### Dates

`dateLocale` (default `en-US`) is a BCP 47 tag such as `hi-IN` or `pt-BR`.
`apps/web/lib/date.ts` exposes `safeDateLocale()` and `formatPublicDate()`;
`PostList`, `RelatedPosts`, `MorePosts` and `Comments` format UTC long dates
with it. The contract normalizer only accepts a language-tag shape, and the
formatter falls back to `en-US` for unsupported/malformed values, so a bad
setting can never throw inside a render.

## Limits

- No language negotiation (`Accept-Language`) or geo-routing.
- API error messages remain English; no timezone choice (dates are rendered in
  UTC, matching the stored instants).
- Menus are literal URLs; no automatic language prefixing and no per-language
  widgets/sidebars/templates.
- Slug uniqueness remains global per type, so translated slugs are suffixed.
- Plain permalinks carry no language context.
- No sitemap `xhtml:link` alternates (hreflang lives in the page head).
- Disabling a language or changing the default changes URLs immediately; no
  redirects are created for the old prefix.
- Comments/notes/revisions/terms are per variant; nothing is synchronised.
